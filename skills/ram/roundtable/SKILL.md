# Council / Roundtable

Use Council for a decision that benefits from independent perspectives. It is
conversation and decision support; Party owns independent execution slices.

1. Bound the question and desired decision. Reuse the user's supplied context;
   do not ask them to restate an existing topic. Search scoped Brain context or
   reuse a fresh receipt matching task, revision, tenant and authority.
2. Resolve two to four available specialists and load their full installed role
   definitions, including voice and reasoning contracts. Use both RAM and Durham
   when the decision spans delivery and experience. Do not guess agent types,
   tool names, permissions or installed roles from a roster description.
3. Invoke the real host delegation tool with the same question, relevant evidence,
   scope and access boundaries. Independent first responses can run concurrently.
   Only request a further reaction if it resolves a material disagreement.
4. Present the actual judgments in distinct voices and preserve disagreements.
   The selected lead owns a concise recommendation, unresolved issues and one
   next action. Agent agreement is not artifact validation or human approval.

If no supported delegation mechanism is available, say Council is unavailable
on this surface and return a proposed brief with question, desired roles and
evidence needed. Loading two personas in one conversation does not execute two
specialists. Never invent a participant, dialogue, consensus or validation receipt.

Use the project's authorized tenant (`allura-system` for RAM by default).
Selecting Durham does not grant its tenant or client access. Pass only context
that may be shared with each participant and honor read-only reviewer boundaries.
Keep the configured runtime and model; do not launch another runtime by inference.
Legacy `/roundtable` or `PM` spellings apply only where the host actually exposes
them. Ordinary requests such as “Council on this decision” are sufficient.
